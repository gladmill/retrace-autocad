# Retrace: notes for contributors and agents

Retrace is an AutoCAD plugin for AutoCAD 2026 (R25.1, .NET 8) and AutoCAD 2024 (R24.3, .NET Framework 4.8): one source, two builds of `Retrace.dll` in one bundle that records manual tests, replays them and builds docs from a customization folder.
The user-facing description is in [README.md](README.md). This file is about working on the code.

## Build, test, pack

```sh
dotnet build Retrace.sln -c Release          # plugin, tests, samples and AcadStatus (the acad-status project, plugin + tests); builds on Mac, Linux and Windows; on Windows also installs the bundles
dotnet test Retrace.sln                      # Retrace and AcadStatus unit tests (net10.0); synthetic fixtures only, no AutoCAD needed. The net48 test project (below) is built, not run, off Windows
scripts/pack.sh /some/out/dir                # builds Release (both targets) and copies the bundle to /some/out/dir/Retrace.bundle; installs nothing
```

- `global.json` asks for the .NET 10 SDK or newer (the tests and `tools/dialog-capture` target net10.0). `nuget.config` restores from nuget.org only, so a feed configured elsewhere on a machine cannot break a fresh clone's build.
- **The bundle.** `bundle/Retrace.Bundle.targets`, imported at the end of `Retrace.csproj`, runs after every build of the plugin. It writes `src/Retrace/bin/<Configuration>/Retrace.bundle` (a fixed path; the outer build, i.e. one without `-f`, deletes and rewrites it): each target's inner build puts its own files in (`Contents/2026/Retrace.dll` + pdb for `net8.0-windows` = AutoCAD 2026 and `Contents/2024/` for `net48` = AutoCAD 2024: its Retrace.dll, pdb and the copy-local dependencies), and the outer build adds `PackageContents.xml` from `bundle/PackageContents.template.xml` (`{Version}` = `<Version>`, `{Series2024}` / `{Series2026}` = `<AutoCADSeries2024>` / `<AutoCADSeries2026>`: two `Components` blocks) and `Contents/` with `scripts/trust-retrace.ps1`, `LICENSE` and `THIRD-PARTY-NOTICES.txt`. A build with `-f net48` or `-f net8.0-windows` only refreshes that target's files and never installs. On Windows outside CI, once the user has started that AutoCAD release (`HKCU\Software\Autodesk\AutoCAD\<series>` has `CurVer`, for R25.1 or R24.3), it then replaces `%APPDATA%\Autodesk\ApplicationPlugins\Retrace.bundle` with that folder (not while the installed dll is loaded) and runs `trust-retrace.ps1 -Series R24.3,R25.1` on it (a release with no profile is skipped; the script touches only these two) (the script exits 2 while any AutoCAD runs). Switches: `RetraceDeploy` (`false`, or `true` to install without a profile), `RetraceTrust=false`, `RetraceDeployDir` (one folder ending in `.bundle`: it is deleted and rewritten). `Retrace.csproj` turns off Visual Studio's fast up-to-date check on Windows, because it would skip the bundle and the install.
- A new AutoCAD release touches: the `AutoCAD.NET` version (per target) in `src/Retrace` and `samples/Retrace.Samples`, `<AutoCADSeries2024>` / `<AutoCADSeries2026>` in `Retrace.csproj` (a new release that runs on the same .NET as a listed one is a new `Components` block in the template, a new series in `<AutoCADSeries>`, no new target; a new runtime is a new target framework), `deps48` in `scripts/pack.sh`, the DocumentFormat.OpenXml version AutoCAD ships in `src/Retrace` and `tests/Retrace.Tests` (below), `DxfRead.VerifiedMajor` and the `acdb<major>.dll` / `accore.dll` export names it calls (`src/Retrace/AutoCad/DxfRead.cs`: re-check `acdbGetAdsName` and `acdbEntGet` on the new release, then raise the version), and the "AutoCAD 2026" wording in the docs.

- `src/Retrace` targets `net8.0-windows` (AutoCAD 2026) and `net48` (AutoCAD 2024), x64, with `EnableWindowsTargeting` and `Microsoft.NETFramework.ReferenceAssemblies`, so both build on any OS. It references `AutoCAD.NET` 25.1.0 (the package for AutoCAD 2026) on net8 and 24.3.0 (AutoCAD 2024) on net48, with `ExcludeAssets="runtime"`: no Autodesk dll is copied anywhere. 25.1.1 is a net10 build and 25.0.x / 26.x are other AutoCAD releases. AutoCAD 2025 (R25.0) is not supported.
- **One source for both targets.** `LangVersion latest` on both. The compiler-support types come from PolySharp (net48 only); `src/Retrace/Compat/NetFramework.cs` (`#if NETFRAMEWORK`) adds the runtime APIs the code calls that .NET Framework lacks, as C# 14 extension members (`Math.Clamp`, `Environment.ProcessId`, `Path.GetRelativePath`, `File.Move(.., overwrite)`, `ZLibStream`, `KeyValuePair` deconstruction, `GetValueOrDefault`, ...), so call sites stay unchanged. Extension members only apply where the type has no applicable member of that name: when a new .NET 8 overload of an existing .NET Framework method is needed, add it as an instance extension. `#if NETFRAMEWORK` (not a separate file) is used only where the behaviour truly differs: `DialogStack.IStackEntry.Resolved` (no default interface members), `DxfRead` (off), `Embedded/Dependencies.cs` (AssemblyResolve instead of AssemblyLoadContext), `Compat/OpenFolderDialog.cs`. **`Path` on net48 is `Compat/NetPath.cs`** (a global using alias, net48 only): `System.IO.Path` throws on `" < > |`, control characters and a mid-path `:` where .NET 8 does not, and names parsed from .rc, .cuix, recordings and settings reach it, so one bad name would lose a whole scan. NetPath has the members the code uses with the .NET 8 results and no exception; write `Path.X`, never `System.IO.Path.X` (it bypasses the alias), and add a member there when the compiler asks. File and Directory calls on an invalid name still differ (ArgumentException instead of IOException): guard them with `File.Exists`, which is false for such a name on both. `PathSafetyTests` covers it on both targets. Do not use `NativeLibrary`, `AssemblyLoadContext`, default interface members, `Range` on arrays or a newer BCL API without checking the net48 build; the nullable warnings (CS86xx) are off on net48 (the BCL has no annotations): the net8 build reports the real ones.
- **net48 dependencies.** `System.Text.Json` 8.0.5 (and with it System.Memory, Buffers, Unsafe, Encodings.Web, Bcl.AsyncInterfaces, Tasks.Extensions, ValueTuple, Numerics.Vectors) and DocumentFormat.OpenXml 2.16.0 stay copy-local and go to `Contents/2024/` (`EmbedDependencies` keeps them for net48 only; `pack.sh` has the exact list in `deps48` and fails on any other dll). Markdig and WebView2 are embedded as on net8. Add a licence to `THIRD-PARTY-NOTICES.txt` for every one.
- `tests/Retrace.Tests.Net48` compiles the same test sources, `Engine/`, `Core/` and `Compat/` for `net48` (plus `TestCompat.cs` for test-only shims). It builds anywhere (part of `Retrace.sln`, so `dotnet build Retrace.sln` is the CI check that Engine and Core compile for .NET Framework) and runs on Windows only (`dotnet test tests/Retrace.Tests.Net48`; off Windows `IsTestProject` is false and `dotnet test Retrace.sln` skips it). On a machine without the SDK, copy its `bin/Release/net48` folder and run `xunit.console.exe Retrace.Tests.Net48.dll` (xunit.runner.console 2.9.3, `tools/net472`). The source-scanning tests (`LayerRulesTests`, `CommandNamesTests`, the Retrace-ribbon test of `RibbonMapperTests`) look for `src/Retrace` and `samples/Retrace.Samples` above the test folder: copy those folders next to it.
- `tests/Retrace.Tests` targets `net10.0` (xunit). It has no ProjectReference: it compiles `src/Retrace/Engine/**` and `src/Retrace/Core/**` directly (globs in the csproj), plus Markdig and DocumentFormat.OpenXml as package references. New files in those folders are picked up on their own.
- Nothing in `AutoCad/` or `Ui/` can run in the tests. Anything worth testing goes in `Core/` or `Engine/`.
- `scripts/pack.sh` checks that both `Retrace.dll` files contain every embedded dependency and the loader name, searches both dlls and pdbs for the checkout's and home folder (UTF-8 and UTF-16) and this account's user name, checks the manifest has exactly the two entries, and fails if the bundle holds any dll or exe that is not `Contents/2026/Retrace.dll` or on the `Contents/2024` list (or a `Contents/Retrace.dll` at all). It needs `python3`. Publish only bundles made by `scripts/pack.sh`: it builds with `ContinuousIntegrationBuild=true`, so the dll and pdb hold no local folder paths.
- **The release zip** holds two folders side by side: `Retrace.bundle` (this `scripts/pack.sh`) and `AcadStatus.bundle` (`acad-status/scripts/pack.sh`, see [acad-status/AGENTS.md](acad-status/AGENTS.md)). Each is made by its own script; zip the two folders, nothing else, and test the zip, not the build output.
- `Retrace.sln` also holds the AcadStatus plugin and its tests (solution folder `acad-status`) because the release zip ships both; `AcadStatus.sln` still builds AcadStatus alone. The public export rewrites the solution's project paths for its layout.
- `samples/Retrace.Samples` is a demo plugin (own dll, not in the bundle) for practising the flow and for VM tests.
- **Status bar clicks (`statusbar_click`).** `AutoCad/StatusBarWatch` reads AutoCAD's status bar, which is WPF (a host window under `msctls_statusbar32`; every item's DataContext is `Autodesk.AutoCAD.StatusBar.Pane` / `PopupPane` / `TrayItem`, read by property name, so a renamed type still works while the properties are there), by a hit test of its visual tree at the button-down (`Recorder.StatusBarInput`, called from `OnPreTranslate` before the item handles the click, only when the point is on the bar), and lists every item for the replay (`StatusBarReplay`: `StatusBarMatch.Find` by key, text, stable part of the text, tool tip, place for an icon; shown and enabled; `RealMouse` with `right` for the right button; the replay window steps aside from the item with `Avoid`). Pure parts (event, wording, matching, what is recorded, the crop) are `Core/StatusBarClick`; the plan step is `Step.Kind` `statusbar` (a command it starts is `origin` `statusbar`, claimed like a palette button's; the dialog it opens is the dialog step after it). The managed `Pane.MouseDown` is not used: it runs after the item's own handler, so a dialog the item opens would block it. Only an add-in's items are recorded: AutoCAD's own (a toggle is relative at replay) are logged and left out; a click during a running command is an inline note of that step (`Step.InlineStatusClicks`, `Plan.Problem` makes the step a person's); `StatusBarMatch.Claims` does not claim a command after a dialog opened; the first click near the bar writes a `status bar probe:` line. `PaneClicks.IsApplicationFrame` keeps the application frame's own WPF (Quick Access Toolbar, title bar, InfoCenter, status bar) out of the `pane click not recorded` line. See docs/recording-format.md, "Status bar clicks".
- **Palette sets with Auto-hide (`opened.state`).** `PaletteSnapshot` also reads a rolled-up floating set (its frame stays on screen as a 22 px strip while its pages are moved off: `PaletteState.Strip`) and the thin edge bar that holds the tabs of anchored docked sets (`PaletteState.IsBar`); `PaletteOpening.Decide` boxes what is on screen (expanded palette, strip, or the edge bar when exactly one new set could be it), says which in the `end picture N:` log line, and judges "there before" per set (a set with any page shown or rolled up was there; one that existed hidden was not); `ShotService.OpenedRecheck` drops a strip box when the set shows expanded at the capture; a not-shown page is logged with its geometry (`PaletteState.Diag`).
- `samples/Retrace.MfcSample` is a real MFC DLL (C++, shared MFC, Unicode, x64; `build.ps1` builds it on the Windows machine with the VS 2022 Build Tools, also on an ARM64 VM through `arm64_amd64`) that `Retrace.Samples` calls (`DRAWMFCFRAME`: a modal `CFrameWnd` + `CFormView` with a `CToolBar`; `DRAWMFCDIALOG`: a `CDialog`). No binary is committed (`.gitignore`). It exists because Win32 stand-ins hid how MFC really lays its windows out.
- AutoCAD only runs on Windows. There a build installs the plugin (above); from macOS or Linux, `scripts/pack.sh` and copy `Retrace.bundle` to `%APPDATA%\Autodesk\ApplicationPlugins\` (see "VM test scripts").

### The layer rule

`Engine/` and `Core/` never use `Autodesk.*`, `System.Windows*` or `Microsoft.Web.*`. `AutoCad/` and `Ui/` may use anything and call down into `Core/` and `Engine/`; the engine never calls up.
`tests/Retrace.Tests/LayerRulesTests.cs` enforces this by scanning the source files, and also that `Engine/` and `Core/` run safely in the AutoCAD process:
no `Console.`, no `Environment.Exit`, `Process.Start` or `AppDomain.SetData`, and no `new Regex(` or static `Regex.` calls (use `Rx.Create` / `Rx.Replace`, which set a 5 s match timeout).

Namespaces follow folders (`Retrace.Engine.Scan`, `Retrace.Core`, `Retrace.AutoCad`, `Retrace.Ui`). A file is named after its main type.

### Engine API

`Retrace.Engine.EngineRunner` is the in-process entry point. Every method is synchronous, never throws, never writes to the console and returns an `EngineResult` (`Messages`, `Warnings`, `Error`, `Cancelled`, `Output`, `Script`, `Docx`, `Xlsx`, `RibbonMap`; `Lines()` for a log).

| Method | What it does |
|---|---|
| `BuildDocs(EngineOptions, CancellationToken)` | Scan the source folder and write the docs folder: reference, guide, test plans, and with `Sessions` the recordings pages and how-tos. |
| `WriteSteps(recording, docx, xlsx, sourceMap)` | `recording.jsonl` -> `steps.md` beside it, pictures renamed after the steps, optional Word and Excel. |
| `Export(path, docx, xlsx)` | Word / Excel from an existing `steps.md` (a recording or test folder is accepted). |
| `AnalyzeRecordings(inputs, output, sourceMap)` | The recordings report alone: `recordings/` and `data/recordings.json`. |
| `WriteTrainingDoc(manifestPath, docxPath)` | The Tdoc Word file from a `tdoc.json` (pictures beside it). `EngineResult.Docx` is the file written. See [docs/tdoc.md](docs/tdoc.md). |
| `MapRibbon(RibbonMapOptions, CancellationToken)` | Read the chosen folders (CUIX / CUI files, ribbon code, LISP, C++, C#, VB.NET) and map every ribbon item to the code it runs, also for the live ribbon the plugin copied (`LiveRibbonReader`). `EngineResult.RibbonMap` holds the rows; with `Output`, `ribbon-map.md`, `.csv` and `.json` are written there. Format: [docs/ribbon-map.md](docs/ribbon-map.md). |

`Retrace.Core.EngineJobs` runs engine jobs one at a time, first in first out (a job started while another runs waits; a second docs build, or a second ribbon map, is refused while one runs or waits), on a thread-pool thread so AutoCAD stays usable. `Cancel()` cancels the running job and drops the waiting ones (their `onDone` gets a cancelled result); `Cancel("map")` does that for the jobs of one kind only (the Map window's Cancel). Every accepted job gets `onDone` exactly once, on that thread. Callers marshal to the UI thread themselves (`Dispatcher.BeginInvoke`); `Commands.StartMap` does it for the Map window and `-RETRACEMAP`. `EngineJobs.DocsOptions(settings)` builds the options from the settings.
Only `BuildDocs` and `MapRibbon` are long enough to check the token: `BuildDocs` between pipeline stages, `MapRibbon` between folders and stages.

### One dll: embedded dependencies

For AutoCAD 2026 `Retrace.dll` (`Contents/2026/`) is the only file of the plugin. (AutoCAD 2024's `Contents/2024/` is the exception, below.) Nothing version-specific sits loose in `Contents/`; 0.6.16 and earlier had the 2026 dll at `Contents/Retrace.dll`, and the manifest no longer names it, so a stale copy left by a copy-over install is never loaded. The docs tell people to replace the whole bundle folder.

DocumentFormat.OpenXml is the exception: AutoCAD 2026 ships 2.16.0 in its program folder and the runtime binds every load of that name to it before any resolver runs (a 3.x build failed in AutoCAD with MissingMethodException). So the csproj references exactly 2.16.0 with `ExcludeAssets="runtime"` and uses AutoCAD's copy. Keep it on the version AutoCAD ships when moving to a new AutoCAD release. Markdig, Microsoft.Web.WebView2.Core / .Wpf and the native `WebView2Loader.dll` are PackageReferences that the csproj target `EmbedDependencies` embeds as resources named `Retrace.Deps.<file>` and `Retrace.Deps.native.<file>`.
AutoCAD does not probe the bundle folder, so `Embedded/Dependencies.cs` hooks `AssemblyLoadContext.Default.Resolving` from a module initializer (before any other type of the dll runs) and loads those assemblies from the resources. If AutoCAD or another plugin already loaded an assembly of that name it uses theirs.

The native WebView2 loader is extracted to `C:\temp\retrace\cache\native\<Retrace version>\Retrace.WebView2Loader.dll` and loaded explicitly through `NativeLibrary.SetDllImportResolver`. It has a private name on purpose:
AutoCAD makes the folders of its plugins visible to the processes it starts, and Autodesk's licensing agent, which outlives AutoCAD, once loaded a plain `WebView2Loader.dll` from there and locked it against updates. A folder per version means a locked old copy never blocks an update.
`pack.sh` fails if the private name is missing from the dll or if the bundle contains another dll. Do not add a plain `WebView2Loader.dll` anywhere in the bundle.

**AutoCAD 2024 (net48).** The embedded resources and their names are the same. `Dependencies.cs` registers `AppDomain.AssemblyResolve` from the module initializer instead: an embedded name is loaded from the resource (`Assembly.Load(bytes)`), any other from a file of that name beside Retrace.dll (`Contents/2024/`, loaded with `LoadFrom`) when its version is at least the one asked for. AutoCAD gives add-ins no app.config, so there are no binding redirects: the framework binds exact versions, a different version of System.Memory, System.Text.Json and so on that another add-in loaded does not satisfy ours, and the handler then loads ours next to it (two versions of a strong-named assembly can coexist). The dependency set is pinned and self-consistent (System.Text.Json 8.0.5 with the versions it declares). Remaining risks: an `acad.exe.config` redirect that sends one of these names to a version Retrace was not built with (it never reaches the handler), and types of these assemblies passed between Retrace and another add-in (none are). The WebView2 loader is extracted as plain `WebView2Loader.dll` into `C:\temp\retrace\cache\native\<version>\net48\` and the wrapper is told the folder with `CoreWebView2Environment.SetLoaderDllFolderPath` (the .NET Framework wrapper cannot be pointed at a renamed file; the folder is not a plugin folder, so the licensing-agent problem above does not apply).

Do not add a dependency without embedding it (net8) or listing it in `deps48` (net48), adding its name to the list in `pack.sh`, and adding its licence to `THIRD-PARTY-NOTICES.txt` (the bundle ships that file).

## Conventions

- **Scanners are heuristic.** The scanners are not compilers. Prefer finding less over reporting something wrong, and say what was missed: `EngineModel.Warnings` (shown in the docs `README.md`). Shared text helpers (comments, braces, arguments, method finding) are in `Engine/Util/CodeText.cs`. `Model.cs` is the contract between parts; scanners do not add fields to it, extras go in the `Extra` dictionaries.
- **Guide merge.** Pages in `docs\guide\` hold engine blocks between `<!-- engine:begin KEY -->` and `<!-- engine:end KEY -->` and owner text outside them. `Emit/GuideMerge.cs` is the pure merge, `Emit/GuideWriter.cs` and `Emit/GuideHowTo.cs` build the blocks. Rules (also in [docs/output-layout.md](docs/output-layout.md)):
  never touch text outside a block; a second run on unchanged input changes nothing; a block whose source disappeared becomes a removed note; broken markers leave the page alone and write `<name>.engine-new.md`; keys must not depend on a step's position (`step:<kind>:<what>:<n>`). Tests: `GuideTests.cs`, `HowToTests.cs`.
- **Reference and generated pages are rewritten every run.** Only `guide\` is owner-edited.
- **Paths.** Build file paths with `Path.Combine` and the other Path APIs. Use `/` only inside markdown links and in the `file` of `shot` events. Every path in the docs folder is named in `Engine/Emit/DocsLayout.cs`; on-disk test folder names and discovery are in `Engine/Recordings/TestFolders.cs` (the one implementation, Core uses it too).
- **`Paths.Root` is a constant** (`C:\temp\retrace`). No environment variable, no setting. Every function takes the root as a parameter so tests can use a temp folder. Do not read `Paths.Root` directly in new code that tests need to reach; pass the root in.
- **No work in AutoCAD event handlers.** Handlers only record data. Screenshots are queued and taken later from a timer or `Application.Idle`; drawing digests are read only in a command or timer context. Do not touch AutoCAD objects inside a `PromptingFor*` handler (reading `PromptOptions.Keywords` there made AutoCAD loop on mouse picks).
- **Errors never reach AutoCAD.** Command bodies go through `RetraceApp.Run`, which logs and prints. Log with `AutoCad/Log.cs` (writes `C:\temp\retrace\retrace.log`). Window handlers do the same: catch, log, and show one line in the window.
- **The live ribbon is copied, not shared.** The engine never sees an `Autodesk.Windows` object: `AutoCad/LiveRibbonReader.cs` copies the ribbon on the UI thread into `LiveTab` / `LivePanel` / `LiveItem` records (`Engine/Map/LiveRibbon.cs`), which the engine reads on its own thread. `Commands.StartMap` takes the copy, and the list of loaded customization files, before it starts the job.
- **Writing files.** Write to a temp file and move it over the target when a reader could see half a file (results, steps.docx, recording.jsonl rewrite).
- **Wireframe fidelity.** Win32 `.rc` and WinForms wireframes are drawn at 100 % / 96 DPI (`Engine/Util/FontMetrics.cs`; `FontMetricsData.cs` is generated by `tools/gen_font_metrics.py`, numbers only, no font files). Compare against real captures with `tools/compare_captures.py <captures> <out>` (needs Pillow and rsvg-convert).
- **Writing style for docs and messages:** short sentences, concrete, no marketing.

## Safety

- The scanner never opens files whose names look like secrets (`InputScanner.LooksSecret`). It lists them as skipped. Keep it that way.
- Test fixtures are synthetic. Do not copy client code, client names or Autodesk SDK files into the repo.
- Recordings and captures are user data: they hold drawing names, typed text, coordinates and object handles. Never commit real ones; tests use synthetic JSONL only.
- Map files are user data too: `ribbon-map.md`, `.csv`, `.json` and `map-folders.json` hold full local paths and the names of the user's buttons, commands and code. Never commit real ones; tests build synthetic folders.
- No secrets, no keys, no personal or company names in code, docs or fixtures.

## VM test scripts (`tools/vm`)

Scripts for a Windows machine or VM that you can reach over ssh, with AutoCAD 2026 and the Retrace bundle installed. They start AutoCAD in the interactive session, send commands over COM, take screenshots and replay a recorded test unattended
(`tools/vm/run-test.sh <test folder> [--new-drawing] [--run]`). A script that records stops with `-RETRACESTOP`, never `RETRACESTOP` (that one opens the Checkpoints window). They are a developer aid, not part of the plugin. The ssh host comes from `RETRACE_VM_HOST` (default `retrace-vm`, an example alias for `~/.ssh/config`).
The scripts live in `C:\retrace-vm\` on the VM. See `tools/vm/README.md` for each script and the lessons learned (session 0 has no desktop, COM calls hang at a prompt, simulated mouse clicks may not reach a VM).
`tools/vm/fixtures.sh` builds fixture drawings (`fx-*.dwg`: layers, layouts, viewports, xdata, extension dictionaries, symbol tables, sysvars, named views, attributes), one-change mutation scripts and a dump query on the VM; see "Fixtures" in the README.
`tools/dialog-capture` (Win32 `.rc` dialog captures, run on Windows) is documented in its own README.

### Commands for scripts

A `-` command is the form a script, LISP or COM automation may run (COM `SendCommand` is not detected by `Ask.ScriptKnown()`: CMDACTIVE is 1 there): command line only, no window, no message box (`-RETRACEMARK`, `-RETRACESTOP`, `-RETRACESETTINGS`, `-RETRACETDOC`, `-RETRACEMAP`, `-RETRACESUITE`). When a stop-path or other command gets a new window, give the `-` form a way around it (`Core/StopReview.cs` decides the Checkpoints window). File pickers are skipped when `Ask.ScriptRuns()` (CMDACTIVE 4 / 32).

### Suite hook in the Replayer

A suite run passes a `SuiteHook` to `Replayer.Start`; it is null for every other replay and then nothing changes. With it: the step timeout (`CheckStepTimeout`: ^C^C, step `timed-out`, verdict ERROR), a dialog or palette step Retrace cannot do ends the test as needs-person instead of waiting, an "open" step for a drawing that was open before the suite opens a temp copy of the file, and Stop ends the suite. `TestQueue` asks its owner (`Gate`) before each test; the suite closes the previous test's drawings there. See [docs/suite.md](docs/suite.md).

### SDI (`SDI` = 1)

With the single document interface AutoCAD keeps one drawing and one `Document` object: opening a drawing fires `DocumentToBeDestroyed`, `DocumentCreated` and `DocumentActivated` for the **same managed object**. Handlers on `Application` and `DocumentManager` (`EnterModal`, `DocumentCreated`...) survive; handlers added to that `Document` (`CommandWillStart`, `CommandEnded`, the editor's) do not, so anything that hooks a document must hook it again on `DocumentCreated` (`Replayer.OnDocCreated`; `Recorder.HookDocument` compares the `Database` it hooked) and must not tell documents apart by object (`SuiteRun` goes by file name under SDI). `DocumentCollection.Add` throws, so RETRACERUN opens a copy of the template.
`AutoCad/SdiDocs.cs` is the one place for it, and every call is a no-op with `SDI` = 0: `Open` (COM `Documents.Open`: after `DocumentCollection.Open` a text sent with `Document.SendStringToExecute` was never executed; after COM `Documents.Open` it still was, in some runs, with its first line lost: `CIRCLE`, `0,0`, `5` ran as `0,0` and `5`, which `UnknownCommand` reported), `Send` (every send of the replay, the suite and the test queue; under SDI, when nothing runs, from a dispatcher callback through the internal command `RETRACETYPE`, which calls `SendStringToExecute` from inside a command and so works; the COM call itself must not be made from the replay's tick: it runs the command, a dialog included, before it returns, and the tick would stop), `PrepareForOpen` (`Core/SdiGuard.Refusal`: never replace a drawing with unsaved changes; a test's own temp drawing is saved with COM `Save`: `CloseAndDiscard` and COM `Close` under SDI end in QUIT). Pure rules and their tests: `Core/SdiGuard`, `SdiGuardTests`.
Which drawings are the test's own: `Core/SdiOwnFiles` (`SdiGuard.Own`): only files this process copied below the real temp folder (`SdiDocs.CopyInto` is the one copy helper, suite copies too); a folder name alone never qualifies. `Replayer.Begin` / `Finish` call `BeginRun` / `SdiDocs.EndRunLater` (the run's drawing is saved on a timer once nothing runs in it; a suite run keeps its drawing own when that fails), so unsaved changes made after it are a person's and `PrepareForOpen` refuses. Typed OPEN / NEW (`SdiGuard.OpensDrawingCommand`) and palette double-click opens stop the replay for a person under SDI; `OnDocCreated` applies the suite's protected-drawing rule. `RETRACETYPE` is registered with `NoUndoMarker | NoHistory | NoActionRecording` so it stays out of U and of Enter-repeat.
The cause of the lost text is not found (it depends on the history of the one `Document`: a drawing opened by `DocumentCollection.Open`, `SDI` switched while AutoCAD ran, and a drawing opened from a timer all had it; the same text sent from inside a command always ran). `EnterModal` / `LeaveModal` were raised for every dialog in every run, so the replay and the recorder need no window polling. When working on SDI on the VM, leave no dialog or verdict box open when you restart AutoCAD: a COM call waiting for it has delivered a stale QUIT to the next AutoCAD.

### The start drawing of a test (RETRACERUN)

A test replays into a drawing Retrace makes (a new drawing, or under SDI = 1 a copy in `retrace-sdi`). `Commands.ChooseTemplate` picks its template (`Core/TemplateChoice`): candidates are the recording's header `template` (a hint: the QNEW setting of the recording machine, written only for a recording started in a new drawing), this profile's QNEW template (`Preferences.Files.QNewTemplateFile`) and `acad.dwt`; the one whose layer names best match the recording's start digest wins (exact match, else fewest missing plus extra; `AutoCad/TemplateLayers` reads each candidate with a side database, cached per path and write time; a UNC path is checked with a 2 s limit). So an old recording or one from a named drawing still starts from `acad.dwt` when that matches, and a company template is used when the recording started from it. Without a digest the header template, else `acad.dwt`. When the start state still lacks layers (recording from another machine, another template), `Replayer.SetUpStartLayers` / `AutoCad/StartSetup` create them from the recording's start state (`Core/StartLayers`: `snapshots/start.json` behavior `layers`, name only for older recordings), only in a drawing that is the test's own (`_ownStart`: RETRACERUN's idle start; never RETRACEREPLAY / RETRACESTEP, which run in a person's drawing), and make the start CLAYER (start.json sysvars, else the digest's current layer) current whenever it differs. It also removes layers the start state did not have when nothing uses them (`Database.Purge` decides; kept ones are reported), so the start state matches whatever the template held. The setup runs with undo recording off for the database, so a recorded U / UNDO cannot undo it, and `SdiGuard.Own.BeginRun` gets the modified flag read before it. start.json is read only when a start layer is missing. Entities of the start drawing are not recreated, so a layer that held entities at the start is created empty (warned: a PURGE may remove it).

### Unknown commands in the Replayer

AutoCAD raises `Document.UnknownCommand` for some commands it then runs: UNITS on a fresh start of AutoCAD 2026 (only the first UNITS of a session; probably the command is loaded on first use; the recording shows `cmd_unknown` about 100 ms before `cmd_start`). `Core/UnknownCommandGrace` decides what the replay does: `Replayer.OnUnknown` and `OnCmdStart` only feed it (field writes), the tick polls it (`CheckUnknown`, which sets `_unknownWaiting`: no next step meanwhile).
The replay tells it every command it sends (`Replayer.NoteSent`: `RunStep` before a ribbon click, `Type`, a palette step before its action and for the right-click command it types; never what a person types, and not the answers typed into a running command). An unknown report that names a command sent in the last 5 s and not started yet gets 2 s to start. A `CommandWillStart` of the same name ends the wait (one info line in `retrace.log`, "carrying on"), even when the tick that would have seen it came late. Every other unknown command, a different one while one is awaited, or one that does not start in time is ERROR "unknown command X" as before.
`Core/CommandName` is the one comparison of command names (case and the prefixes `_ . - * '` ignored); `RecordingSession` uses it for its macro commands and to drop a `cmd_unknown` that a `cmd_start` of the same command follows, so the readers and the replay agree. `Plan` and `StepTally` never made a step of `cmd_unknown`. `UnknownCommandGraceTests` covers both sides.

### Pictures and screen coordinates (`AutoCad/ScreenSpace.cs`, `Core/MarkGuard.cs`)

AutoCAD is system DPI aware. When its monitor's scale is not the one it started with (the scale was changed after sign-in, or the window is on a second monitor with another scale) Windows bitmap-scales it: everything AutoCAD's own thread reads (`GetWindowRect`, `ClientToScreen`, mouse messages, WinForms bounds) is in that scaled "logical" space, while the screen, DWM's frame bounds and `BitBlt` are physical pixels. **Every rectangle and point in Retrace stays logical** (it is also the space `SetCursorPos` and the replay's clicks use, so clicks need no conversion) and only the capture converts: `ShotService` turns the logical rectangle into physical pixels for the `BitBlt` and DWM's bounds back into logical ones (`ScreenSpace.ToPhysical` / `ToLogical`, by the window's own logical and physical rectangles, the latter read under a per-monitor-aware thread context). A `ShotService.Picture` is the logical rectangle (`Left`, `Top`, `SrcWidth`, `SrcHeight`) at physical resolution (`Width`, `Height`); frames and arrows are mapped by ratio. Never read a rectangle under another thread DPI context and mix it in. `Core/MarkGuard` is the rule for marks: a frame or arrow is drawn only when its rectangle lies inside the picture's rectangle and, when a click point is known, contains it; a toolbar item's rectangle must lie inside its strip's client area. The `LogicalToPhysicalPointForPerMonitorDPI` API was tried and is the identity for a system-aware window: do not use it.

**Smart zoom (setting `screenshotMode`, `smart` by default; `classic` stays a choice).** `Core/SmartCrop` is the one pure decision: from the picture kind (ribbon / palette / dialog / drawing) and the logical rectangles known for it (item, panel, tab headers, active tab, whole ribbon, palette, window) it returns the crop rectangle (item + panel + active tab and two neighbours each side + 24 px, at least 600 x 360, inside the window; a missing rectangle gives the whole ribbon, then the window; dialog and drawing pictures are the window). `AutoCad/SmartShots` reads the rectangles from the ribbon's WPF tree (`TdocTargets.RibbonItemRect` for the item, one walk for the panel and the tab headers) and copies the crop; `ShotService.Write(..., keepSize: true)` and `TdocCapture.Save(..., keepSize)` skip the 1400 px scale-down, so a smart picture is a 1:1 copy. `classic` takes none of these paths and shows one picture per step, the whole window: `Recorder.PaletteClickPicture`, `EmitContextMenu` and `EmitPalette` write no palette close-up (the scheduler's window picture, with the frame and arrow noted for the clicked item, is the step's picture), and `TdocCapture.ShootPalette` takes the window (the palette's own frame only when it lies outside AutoCAD's window). In smart mode a palette step's `window` picture is suppressed when its crop is certain (`ShotService.Suppress`). Classic keeps one fallback capture, the palette close-up taken at the press (`PaletteWatch` takes none while the person works unless smart): `ShotService.ExpectWindowPicture` holds it and `PictureFallback` (Core) writes it only when the step's window request never produced a picture (dropped after `ShotScheduler.MaxWaitMs`, or AutoCAD's window not shown); a palette outside AutoCAD's window (`ClassicPalettePicture.InsideWindow`, `Recorder.PaletteInsideMain`, same test in `TdocCapture.ShootPalette`) uses the close-up as the one picture (the window request is suppressed). Nothing is filtered when documents are built: an older recording's palette steps show what it holds (a close-up next to the window picture; the recording cannot tell a docked palette from a floating one), and the header's mode (`SettingsHeader.ModeOf`: a header without `settings` or without `screenshotMode` is classic, never the current default) is only used for the not-default line. **Ribbon click marks:** `Core/RibbonMark` decides the green box and arrow of a ribbon click's picture: the clicked item's own rectangle read at the click (`TdocTargets.ItemRectAnywhere`: the item object, not a lookup by id, in every WPF source of the process, so a drop-down or slide-out is found and an id used on two tabs is not mixed up), else the button that holds it (split / drop-down), else an arrow at the mouse-down point (`Recorder._downX/_downY`, fresh for 1 s and only when the press was in a WPF window: a click in the drawing followed by a keytip-run button is no press on that button; a rectangle the picture does not show is unusable, so the next candidate is tried; the container is looked up only when the item's box is not used and only if it is button-like, never a row panel; only the ribbon's own source and pop-ups are searched, each source guarded; one `retrace.log` line per ribbon click gives the result and the lookup time), else nothing and a `retrace.log` line says why; a rectangle that does not hold the mouse-down point is not used. `ShotService.MarksFor` logs every mark it leaves out. `samples/Retrace.Samples/MarkTestTab.cs` (`DRAWMARKSTAB`) builds the ribbon cases for checking this on the VM. Rectangles stay logical (the rule above); never add a physical one.

### Tdoc hooks in the Replayer

A Tdoc run (`AutoCad/TdocRun.cs`) is the RETRACERUN path with a `TdocCapture` handed to `Replayer.Start`. Every hook is a no-op while that field is null, so a plain RETRACERUN / RETRACEREPLAY behaves as before; keep it so.
`Replayer`: `BeforeStep` (a gate in `Tick`, before the step runs), `AfterStep` (a checkpoint's result), `AfterCommand` (a gate at the top of the tick once the replay has settled after a command's last dialog: the picture of the step of the prompts given after the dialogs, `TdocSplit`) and `AfterDialog` (the same, between two dialogs of one command, called from `Replayer.TickDialog` when the next dialog step is already open, which skips `BeforeStep`; from `BeforeStep` of the next dialog step otherwise), `AnswersTyped` (the replay typed those prompts; a step whose prompts never were is dropped when the test ends), `DialogReady` (the `DialogAutoFiller.BeforeClose` gate: the picture of the filled dialog is taken before OK is pressed; the UI Automation fill stops before the click when it is set) and the `finished` callback at the end of `Finish`.
Gates return false until ready and are asked again on the next 200 ms tick; nothing blocks the UI thread, and UI Automation runs on a pool thread only. See [docs/tdoc.md](docs/tdoc.md).

### Evidence hooks in the Replayer

An evidence run (`Run with evidence`, `-RETRACEEVIDENCE`) is the RETRACERUN path with an `EvidenceCapture` handed to `Replayer.Start` (`Commands.Test` makes it only for the recording the evidence run queued, never for a suite or Tdoc run). Like the Tdoc hooks every one is a no-op while the field is null; keep it so.
`Replayer`: `AfterPrevious` (a gate in `Tick`, next to Tdoc's `AfterCommand`: the step before has run and settled; it hides Retrace's windows, takes the picture and shows them again inside one call with a `finally`, so no tick leaves a window hidden), `Failure` (from `Finish` when the run ended early, with the step `_acting` that was being run and how it ended) and `Finished` (the workbook is written on a pool thread). How the replay's steps become the sheet's rows and results is `Core/EvidenceMapping` (pure; add a case to `EvidenceSheetTests` for any rule you change); the workbook itself is `ExportXlsx.Write(..., EvidenceData)`. Nothing here may write steps.xlsx. See [docs/evidence.md](docs/evidence.md).

### Status board hooks

Retrace writes `retrace-<acad pid>.json` to the AutoCAD status board (format: [acad-status/CONTRACT.md](acad-status/CONTRACT.md); user note: README "Status board").
`AutoCad/StatusBoardHost.cs` is the only place that touches the file; everything else is a one-line call into it, and every call is a no-op when the setting `statusBoard` is off.
- `StatusBoardHost.Start()` / `Shutdown()` from `RetraceApp.Initialize` / `Terminate`. The 3 s timer is a `DispatcherTimer` on the UI thread (the project does not reference WinForms on purpose): a hung UI thread stops it and the file goes stale, which is the design.
- `Changed()` from the Replayer's 200 ms tick, the end of `Recorder.Stop` / `Detach` and `TestQueue.Next`; it writes only when the entry differs from the file. `ReplayStarted` / `ReplayEnded` from `Replayer.Begin` / `Finish` (the end is reported before the verdict box, which blocks), `RecordingStarted` from `Recorder.Start`, `RunStarted` / `SuiteEnded` / `TdocEnded` from the suite and Tdoc runs, `UserClicked` from the ribbon handler and the Open test window.
- Never call it from an AutoCAD event handler (handlers only record data; `Recorder.StepCount` is a plain counter the timer reads, bumped in `NoteContext` through `StepTally` / `StatusBoard.CountsAsStep`, the replay plan's rule for what is a step). If working out the entry throws, the host logs it once (re-armed by the next good one) and writes `StatusBoard.ErrorEntry` (`error`, "status board error: <exception type>"), so the file never just stops. A status write must never throw into, or wait in, a replay or recording: `StatusWriter.Publish` catches everything, logs the first failure once and tries a failed write again at the next call (a reader that holds the file for a moment must not make the heartbeat slip past the ttl of 15 s); only after 3 failures in a row does it wait (3 s, 6 s, 9 s, at most 10 s; forced writes too; only the last word at Terminate ignores it), so an unwritable `ACAD_STATUS_DIR` costs a replay a few failed writes per 10 s. The folder is created for the first write and again only after a failure.
- "Rec N" follows the plan's script-chain rule (`Plan.ScriptChain`) as far as it can be known live (`StepTally`, fed the event time, command name and `input` flag): a ribbon click whose LISP runs SCRIPT is one step, and the typed/other commands or LISP forms that start within `Plan.ScriptGapMs` of the previous end are not counted until a person's input. The two things it cannot know live: the plan keeps a click split when a person answered before the chain's first dialog, and it ends the chain before a later command that holds a person's event (palette click, tab); the tally counts both as one step. `StepTally` counts a chain's LISP at once and takes it back when SCRIPT starts inside it, so "Rec N" may drop by the LISP's steps at that moment.
- `owner` is `user` (a Retrace button was clicked), `suite`, `tdoc`, or left out. Retrace cannot tell a typed command from a COM `SendCommand` (CMDACTIVE is 1 for both), so it never writes `COM`. The owner is decided once per command invocation: `RetraceApp.Run` calls `CommandStarted(name)` / `CommandEnded(name)`; for RETRACERECORD / RETRACEREPLAY / RETRACERUN / RETRACESTEP `CommandStarted` asks `StartOrigin.Take` (whole command word, the click is used up, 15 s window) and the run takes the answer when it begins. A click therefore never reaches a later typed or COM invocation. The answer is dropped when RETRACERECORD / RETRACEREPLAY / RETRACESTEP return (their run starts inside the command, however long the person takes at its prompt); RETRACERUN's is kept for 65 s from the moment the command returns (its file picker may take any time), because its replay starts when the new drawing is ready. A recording and a replay keep their owners apart.
- A run that stopped because a step needs a person calls `Finish(..., needsPerson: true)` in the Replayer; only then (and only while a dialog or security prompt is open) is the idle entry needs-person (`StatusBoard.EndOfReplay`). The same for a suite stopped by its gate (`EndOfSuite`); a replay, suite or Tdoc run with an ERROR ends in state `error`.
- `statusBoard` is read with `RetraceSettings.TryLoad` when `settings.json` changes; a file that cannot be parsed keeps the previous value and is tried again at every check (`Load` would give the defaults, which turn the board on). Turning it off writes `stopped`, retried at every tick until it is written.
- The contract is versioned (`v` 1): fields are only added. Change a text in `Core/StatusBoard.cs` and its test in `StatusBoardTests` together; the add-in reads `state`, `short`, `summary` and the `detail` of the contract.
